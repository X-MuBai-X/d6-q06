## 一、现象

自编验收 Skill `skills/acceptance-audit/scripts/acceptance_audit.py` 判定 **R4-01 FAIL**，
理由为「回调鉴权或异常事件缺失」。原判据写的是：

```python
sign_ok = "VerifySignature" in httpapi and "EventSignatureInvalid" in read(repo, "internal/service/anomaly.go")
```

即要求 **domain 层的常量名字符串** `EventSignatureInvalid` 出现在 **service 层文件** `internal/service/anomaly.go` 中。

## 二、责任方判定

**判定：判据本身有缺陷，业务实现无缺陷。** 理由（均已人工核实，位置见下）：

| 要件 | 真实实现位置 | 现状 |
| --- | --- | --- |
| 回调验签 | `internal/httpapi/server.go:219` 调用 `supplier.VerifySignature(...)` | 已实现 |
| 签名无效异常记录 | `internal/httpapi/server.go:220` 记录 `domain.EventSignatureInvalid` | 已实现 |
| 未知任务回调异常 | `internal/service/callback.go:56` 记录 `domain.EventCallbackUnknown` | 已实现 |
| 重复回调不重复建候选 | `internal/service/callback.go:72` 使用 `domain.EventCallbackDuplicate` | 已实现 |
| 事件类型常量定义 | `internal/domain/types.go:165,176,179`（`EventCallbackUnknown` / `EventCallbackDuplicate` / `EventCallbackConflict` / `EventLateResultIgnored` / `EventSignatureInvalid`） | 已实现 |
| 验签失败路径断言 | `internal/httpapi/httpapi_test.go:321-349` | 已覆盖 |

本项目的分层约定是「事件类型属于领域模型，常量集中在 `internal/domain/types.go`」，
异常**记录动作**属于业务层（service）与接入层（httpapi）。
原判据把「事件类型定义位置」与「异常记录实现位置」混为一谈，导致把正确的分层实现误判为缺失。

**同时仍做一处真实代码改进的理由**：判据错 ≠ 现场没有可改进点。
排查中发现「哪些事件种类属于运营异常」这一清单在 `internal/store/candidates.go` 里
以字面量重复维护一份，与 `internal/service` 的异常记录职责割裂（存储层硬编码了业务口径）。
因此借本次闭环做一处真实且必要的重构，而不是为迎合判据做字符串搬家。

## 三、改了什么

### 3.1 代码改进（业务侧，非字符串搬家）

- `internal/service/anomaly.go`
  - 新增导出注册表 `service.AnomalyKinds []string`：异常事件种类的唯一事实来源，取值全部来自 `internal/domain/types.go` 已存在的常量
    （`EventCallbackDuplicate`、`EventCallbackConflict`、`EventLateResultIgnored`、`EventSignatureInvalid`、
    `EventCallbackUnknown`、`EventGenerationRejected`、`EventGenerationFailed`、`EventGenerationTimeout`），未臆造常量名。
  - 新增判断函数 `service.IsAnomalyKind(kind string) bool`：注册表内返回 true，其余（含空串与自定义串）返回 false。
- `internal/service/query.go`
  - `ListAnomalies` 改为传入 `AnomalyKinds` 查询，并按 `IsAnomalyKind` 二次过滤；
    `Overview` 同样改用 `AnomalyKinds`。
- `internal/store/candidates.go`
  - `ListAnomalyEvents(ctx, kinds []string, limit int)` 改为由调用方给出异常种类清单，动态生成 `IN` 占位符，
    删除原先硬编码的 8 个字面量（去重，不新增重复事实来源）。
  - 改这一处的理由：`service` 依赖 `store`，反向依赖会形成导入环；「异常种类口径」属业务策略，
    故注册表留在业务层、存储层只负责按清单过滤。**行为等价**：清单内容与原 SQL 完全一致，查询顺序与 LIMIT 逻辑不变。
- `internal/store/store_test.go`
  - 随签名调整更新调用（断言未削弱，另补一条「空清单返回空列表」的断言）。
- `internal/service/anomaly_test.go`（新建）
  - `TestAnomalyKindsRegistry`：注册表内每个 kind 都返回 true；无重复项；题面 R4 要求的 8 类异常全部已注册。
  - `TestIsAnomalyKindRejectsUnregistered`：`""`、`custom_kind`、`requirement_created`、`callback_accepted` 均返回 false。
  - `TestListAnomaliesUsesRegistry`：运营查询到的异常全部属于注册表；签名无效异常可查；普通事件不混入异常列表。

### 3.2 Skill 判据修正（`skills/acceptance-audit/scripts/acceptance_audit.py`，R4-01）

判据改为**按真实实现位置**判定，仍严格检查三件事：

- (a) 回调验签：`internal/httpapi/server.go` 中存在 `supplier.VerifySignature` 调用；
- (b) 签名无效异常可记录：`EventSignatureInvalid` 在 `internal/domain/types.go` 有定义，
  且 `domain.EventSignatureInvalid` 在 `internal/httpapi/server.go` 或 `internal/service`（排除 `_test.go`）中被真实用于记录事件；
- (c) 重复回调不重复建候选 + 未知任务回调可查：`internal/service/callback.go` 中同时出现
  `EventCallbackDuplicate` 与 `EventCallbackUnknown`。

FAIL 分支保留：缺哪一项就在「证据」里点名缺哪一项，并在「复验方式（整改动作）」中写出对应整改项；
**未改成无条件通过**。脚本中已加注释说明分层原因与依据的文件位置。

负向验证（见 `复检日志.txt` 末尾）：在仓库副本上删掉验签调用并把 `EventCallbackDuplicate` 换成 `EventCallbackIgnored` 后重跑，
R4-01 确实 FAIL 并逐项点名缺失，说明判据未被放宽。副本建在会话工作区临时目录，未改动仓库源码，验证后已清理。
