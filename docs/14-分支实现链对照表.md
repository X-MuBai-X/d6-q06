# 14 · 分支实现链对照表（题目 06）

> 用途：把**每一条业务规则、每一组场景、每一条题面与共同要求**从「题面原文」一路对到
> 「实现文件（文件:行号）→ 数据库表 → 接口 → 页面 → 单元测试 → 场景脚本断言 → 证据位置」，
> 使「题面 → 实现 → 验证」的链条可**逐条定位**，而不是只看最终文件或提交总数。
>
> **本文件的适用范围与生成方式**：
> - 本表的全部行号由对仓库现状的实测定位得出（逐文件 grep/read），**不是**从其他题目的文档沿用；
> - 「状态」列只有三种取值：**已核对**（实现与验证位置均可在仓库内回源）、
>   **待补证**（该项尚未产生可回源产物）、**待核验**（实现存在但证据文件缺失）；
> - 本表**不声称**任何尚未发生的执行结果：远端推送、PR、CI、合并、部署、场景日志、
>   独立测试与独立验收报告在工作项编号核验前一律标「待补证」。
> - 取材：题面 `docs/_question-06.md`；共同要求 `docs/_common-requirements.md`；
>   需求 `docs/01-需求分析.md`；计划 `docs/03-任务规划.md`；部署 `docs/04-部署与使用说明.md`；
>   实现 `internal/`、`cmd/`、`scripts/`、`.github/workflows/ci.yml`、`Dockerfile`；
>   证据 `evidence/`；Skill `skills/`、`skill-usage.md`。

## 7. 本对照表的使用说明

1. 本表**不是**提交清单，也不是完成度自评；它是**定位工具**：
   任何一条 R/S 都能从本表出发，在仓库内找到实现行号、测试用例与证据位置。
2. 表中「状态」为**待补证**时，表示**证据文件尚未产生**，而不是「检查未通过」；
   两者在本表中严格区分（例：R4-01 属「待核验」——检查已做但判定口径待修正）。
3. 行号随代码变动会漂移；复核时以文件内容为准，必要时重新定位。
4. 本表与 `docs/10-交付与发布说明.md` 互为索引：交付索引按**交付物**组织，本表按**业务规则**组织。
