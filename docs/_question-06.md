## 业务背景与现场情境

一家内容团队使用 AI 图片服务为营销活动制作配图。业务人员填写素材需求，平台提交供应商生成，
设计人员查看候选结果，业务人员确认采用或要求重做，运营负责核查长期未完成和异常生成任务。
供应商完成任务只代表生成了图片，并不代表业务已经接受交付。

一次活动准备中，有需求第一次生成正常但图片不符合文案，需要修改描述再生成；另一个需求因供应商失败需要重试；
还有需求已被业务撤销，供应商却稍后发回成功结果。
若系统把供应商任务和业务需求混为一谈，就可能把旧图片当作最新交付、用迟到回调恢复已撤销需求，或者对同一点击创建多个任务。

请实现从素材需求创建、AI 生成、内部复核、重做到最终确认或撤销的完整场景，
业务人员能看到进展，设计人员知道该审核哪一版，运营能跟进异常。

## 参与角色与业务起点

- 需求人：创建需求、修改未执行内容、发起生成、确认采用或要求重做、撤销。
- 设计复核人：查看最新候选图片，给出通过或不通过及原因。
- 运营：查看异常回调、失败和超时任务，跟进并记录处理意见，**无权代替需求人确认采用**。
- 模拟生成供应商：受理任务并通过回调报告结果。

预置两名需求人、一名设计复核人和运营账号，仅支持文本生图，每次生成一张演示图片。

## 需要完成的业务范围与规则

1. 需求包含活动名称、用途和图片描述；需求人确认后发起生成。每次生成须保存当时描述，历史记录不能被后续修改覆盖。
2. 同一需求最多有一个处理中生成任务；同请求编号重复发起不创建第二个供应商任务。本题模拟提交明确返回接受或拒绝，不处理提交结果未知。
3. 供应商提交拒绝、处理失败或 60 秒内无有效终态都不能产生候选交付。失败或超时后，需求人可修改描述并发起下一次生成，最多三次，不要求自动重试。
4. 成功回调需鉴权、关联已知任务并提供图片地址；重复回调不重复创建候选，已终结的生成任务不被迟到或冲突回调改写，异常须可查询。
5. 最新成功结果先由设计复核人审核；未通过须写原因，需求人可重做。复核通过后，需求人可确认采用或提出重做原因；确认采用才算交付完成。
6. 一旦发起下一次生成，上一次候选只作历史，不能再被审核或确认。页面须明确当前候选和历史候选，不能展示旧图却操作新任务。
7. 需求人在确认采用前可撤销；本地撤销不保证供应商停止执行，后续结果仍保留审计，但不得恢复需求或变成交付。已确认采用不在本题中撤销。
8. 需求人仅访问自己的需求；复核人可审核待处理需求；运营查看生成及异常记录。可按需求查清每次描述、供应商任务、结果、复核及最终处置。

## 必须演示的完整工作场景

- 正常交付：需求创建 → 生成 → 设计通过 → 需求人确认 → 运营查询完成记录。
- 业务重做：成功结果被设计退回，或设计通过但需求人不采用 → 修改描述再生成 → 新版本确认，旧版本不能误交付。
- 技术失败：供应商拒绝、生成失败、超时 → 需求人重试 → 历史原因仍可追溯。
- 中途撤销：生成中撤销 → 供应商迟到成功 → 需求继续保持撤销，运营可查询处理原因。
- 并发与权限：重复发起、旧回调晚到、重复复核、他人需求访问及第三次后再次重做均得到明确结果。

## 原型、Skill 与单日边界

原型须覆盖需求工作台、候选复核、版本历史及运营异常查询。
业务 Skill 用于检查需求状态、生成次数、当前候选、复核、交付与撤销之间的约束。

使用演示图片地址和模拟供应商，不做真实生图、图片编辑、下载打包、计费或多级审批。
**须执行第一部分全部要求，不能只交异步任务轮询接口。**

## 共同要求中对本题最关键的几条（全文见 docs/_common-requirements.md）

- 阶段顺序固定：需求分析 → 原型设计 → 任务规划 → Agent 开发 → Agent 测试 → Agent 验收 → 自动部署上线；
  每阶段产物**先落盘**再进入下一阶段，不许开发结束补造过程记录。

- 至少自编两个 Skill（业务专项 + 验收检查），七要素齐全，判定逻辑写在脚本里，必须有真实调用记录，
  并至少展示一次「检查发现问题 → 修正 → 重新检查」。
- 单元测试语句覆盖率整体 ≥85%，各核心业务包分别 ≥85%；并发要求要有可重复执行的验证。
