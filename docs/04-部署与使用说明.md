# 04 · 部署与使用说明（题目 06）

> 本文件说明**如何运行、如何验证、如何回退**。所有命令都是真实执行过的（见 `evidence/` 下的原始日志）。

---

## 1. 环境要求

| 项 | 要求 | 本次实测 |
|---|---|---|
| Go | 1.27+ | `go1.27.1 windows/amd64` |
| Python（仅脚本与 Skill 使用） | 3.10+ | `Python 3.14.8` |
| 第三方依赖 | 仅 `modernc.org/sqlite`（纯 Go 驱动，**无需 CGO**） | `go.sum` 已锁定 |
| 数据库 | SQLite 单文件（默认 `data/studio.db`） | 重启后数据仍在，已实测 |
| 端口 | 平台 `:8080`，模拟供应商 `:8090` | 部署脚本会做端口预检 |

---

## 2. 数据库选择说明（共同要求 §1.3 要求「数据库类型自行选择并说明」）

| 项 | 说明 |
|---|---|
| 类型 | SQLite（`modernc.org/sqlite`，纯 Go 实现） |
| 为什么 | 教学规模下单文件零运维；**纯 Go 驱动不引入 CGO**，避免编译环境差异；SQLite 的部分唯一索引可以直接表达题面 R2「同一需求至多一个处理中任务」与「同请求编号不重复建任务」两条结构性约束 |
| 初始化 | `internal/store/schema.sql` 在 `store.Open` 时幂等执行（`CREATE TABLE IF NOT EXISTS`） |
| 变更文件 | `internal/store/schema.sql` 是结构的唯一事实来源 |
| 持久化验证 | 重启服务后重新查询同一需求，结果仍在（见 `evidence/independent-test-report.md` 的持久化用例） |

## 3. 本地运行


## 4. 模拟生成供应商（可控场景）

`cmd/mockgen` 提供两个控制入口：

| 接口 | 作用 | 示例 |
|---|---|---|
| `POST /control/mode` | 设置**下一次**提交的行为：`success` / `failure` / `reject` / `timeout`，可选 `delay_ms` 与 `duplicate` | `{"mode":"failure","delay_ms":100}` |
| `POST /control/redeliver` | 重新投递一次回调（构造「迟到回调」场景），参数 `ref`（平台侧任务 ID）、`status`、`image_url` | `{"ref":"task-xxx","status":"succeeded"}` |

| 模式 | 平台侧表现 | 对应题面规则 |
|---|---|---|
| `success` | 受理后回调成功 → 生成候选 | R1/R4 |
| `failure` | 受理后回调失败 → 不产生候选，需求可重试 | R3 |
| `reject` | 提交即被拒绝 → 不产生候选，失败原因留痕 | R2/R3 |
| `timeout` | 受理后**不回调** → 平台超时巡检判定超时 | R3 |
| `duplicate=true` | 成功结果连发两次 → 平台必须忽略第二次 | R4 |

> 这是**可控的 HTTP 模拟服务**，不是真实第三方接入成果（共同要求 §1 第 5 条）。

## 5. 质量门禁与场景验证

```bash
# 一条命令跑完 gofmt + go vet + 单测 + 覆盖率门禁（CI 与本机共用同一脚本）
./scripts/quality_gate.sh

# 五组完整工作场景端到端验证（需要平台与模拟供应商都在运行）
python scripts/verify_scenarios.py --base http://127.0.0.1:8080 --mock http://127.0.0.1:8090

# 自编 Skill：业务不变量检查
python skills/material-guard/scripts/material_guard.py --repo . --db data/studio.db

# 自编 Skill：验收检查
python skills/acceptance-audit/scripts/acceptance_audit.py --repo .
```

覆盖率统计口径只有一份实现：`scripts/coverage_gate.py`。它会**先删除旧剖面**、
用**绝对路径**产出本轮剖面，再解析剖面按语句数统计 `covered/total`（与 `go tool cover` 一致）。
**任何**排除项都没有登记——自编的数据库访问与 HTTP 处理代码全部纳入统计。

## 6. 部署（流水线与手工等价流程）

### 6.1 流水线

`.github/workflows/ci.yml` 两个作业（作业名即主分支保护规则中要填的检查项名称）：

| 作业名 | 步骤 |
|---|---|
| `quality-gate` | 检出 → 安装 Go → **gofmt 格式检查** → **go vet** → **单元测试（含 `-race` 竞态检测）** → **覆盖率门禁（≥85%）** → 归档覆盖率原件 |
| `deploy` | 检出 → 构建二进制 → 构建镜像 → **执行 `scripts/deploy.sh`（含端口预检、启动、健康检查、业务冒烟）** → **健康检查** → **业务冒烟（跑五组场景）** → 归档部署证据 |

触发时机：`push` 到 `main` 或 `dev/**`、`pull_request` 到 `main`。

### 6.2 手工执行部署脚本（与流水线同一脚本）

```bash
./scripts/deploy.sh <合并提交 SHA> http://127.0.0.1:8080
```

脚本行为：端口预检（占用即失败退出，避免测到旧进程）→ 构建 → 启动模拟供应商与平台
（stdout 重定向到文件）→ 健康检查轮询 → 跑五组场景冒烟 → 打印部署版本与回退办法。

### 6.3 上线冒烟检查项

| 检查 | 判定 |
|---|---|
| `/healthz` | 返回 `{"ok":true,...}` |
| 五组场景脚本 | 全部断言通过（`scripts/verify_scenarios.py` 退出码 0） |
| 冒烟日志 | `evidence/scenario-verify.log` 中「失败 0 项」 |

## 7. 回退与撤销

| 场景 | 操作 | 说明 |
|---|---|---|
| **回到上一可用版本** | 用**上一个合并提交 SHA** 再次执行 `scripts/deploy.sh <上一 SHA>`，或把部署目标切回上一版本的镜像标签 `creative-studio:<上一 SHA>` | 平台不保存可变状态在镜像内，业务数据在 `data/studio.db`，回退版本后数据仍在 |
| **首次部署失败** | 终止平台与模拟供应商进程、删除 `data/studio.db`、清空 `logs/` 后重新执行部署脚本 | 首次部署没有上一版本可回退，只能撤销本次发布；脚本开头的端口预检可避免"测到旧进程" |
| **数据回滚** | 关闭服务后用 SQLite 工具恢复 `data/studio.db` 的备份文件 | 教学规模下未实现自动备份，见 `docs/10-交付与发布说明.md` 的局限登记 |

## 8. 已知限制（如实登记）

1. **不实现真实生图**：图片地址指向平台本地生成的 SVG 演示图（题面明确「使用演示图片地址」）。
2. **不做图片编辑、下载打包、计费与多级审批**（题面单日边界的明确要求）。
3. **不处理「提交结果未知」**：提交供应商时若 HTTP 调用异常，按「提交失败」收口并留痕（假设 A6）。
4. **不实现注册登录全套流程**：账号预置，使用口令登录换取服务端会话令牌。
5. **不使用真实短信**：站内审计事件代替通知。
6. **未启用真实 2FA / 企业 SSO**。
7. **业务数据无自动备份**：教学规模下由人工复制 `data/studio.db` 备份。
