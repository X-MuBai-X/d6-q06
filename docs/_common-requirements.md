# 共同要求摘要 · 题目 06

> 本文件是《Go项目业务场景题》「一、所有题目共同适用的要求」第 1–10 节的**执行摘要**，
> 便于开发、测试与验收 Agent 在独立上下文中读取。
> **与原始题面冲突时以原始题面为准**（原始题面文件：`docs/_question-06.md`）。

| 节 | 主题 | 对本题的硬性要求 |
| --- | --- | --- |
| §1 | 实现范围与环境 | Go 实现完整业务闭环；必须有可操作的最小业务页面；必须用数据库保存核心业务数据（重启后仍可查）；第三方用可控 HTTP 模拟服务并能触发成功/失败/超时/重复通知；各业务分支可实际操作且有持久化结果；时间边界可用可配置教学时钟但**必须注明** |
| §2 | 必须完成的开发流程 | 需求分析 → 原型设计 → 任务规划 → Agent 开发 → Agent 测试 → Agent 验收 → 自动部署上线；每阶段产物先落盘；三个 Agent 角色使用相互独立的会话或任务上下文 |
| §3 | AI 规则约束 | 开发前编写并实际使用项目级 `AGENTS.md`；保留历史版本与读取记录；禁止编造、禁止弱化断言凑覆盖率、禁止泄露密钥 |
| §4 | 自编 Skill | 至少两个（业务专项 + 验收检查），七要素齐全，可被所用 AI 工具使用，有真实调用记录；至少一次「发现问题→修正→复检」；提交 `skill-usage.md` |
| §5 | 会话导出与 AI 使用记录 | 导出全过程可见会话与结构化事件清单（JSON/JSONL），另交一页 AI 使用说明 |
| §6 | 测试与 AI 产出质量 | 单元测试语句覆盖率整体 ≥85% 且各核心包分别 ≥85%；覆盖正常/边界/非法状态/重复操作/权限/异常路径；并发可重复验证；gofmt、go vet、竞态检测；提交原始输出与覆盖率原件 |
| §7 | 自动部署与最终提交 | 仅对经 PR 合并且门禁通过的主分支版本发布；流水线含质量检查、覆盖率门禁、构建、部署、健康检查、业务冒烟；提交运行地址、流水线标识、部署版本与回退办法；最终交付清单 9 项齐全 |
| §8 | GitHub 仓库、分支与合并 | 开发前经 **GitHub MCP** 建仓；业务提交全在 `dev/<题号>`；main 禁止直推、须 PR 合并并通过状态检查；合并后以合并 SHA 重跑门禁与部署；仓库内保留可审计索引 |
| §9 | 提交规范与工作项校验 | `[类型] [版本号] [需求/Bug编号] 中文描述`；feat/fix 前用 meegle CLI 核验编号并留原始输出；不得伪造编号或声称查询成功 |
| §10 | 每日完成量、群提交与视频 | 当天班级群提交（姓名、日期、题号题名、仓库、PR 与发布版本、部署地址、报告索引、视频）；讲解与效果视频必须本人讲解并展示运行效果，覆盖五组场景 |

## 不得判定整题通过的七条红线

1. 关键业务验收不通过；
2. 覆盖率未达标（整体 <85% 或任一核心包 <85%）；
3. 缺失自编 Skill 或使用记录；
4. AI 过程无法追溯；
5. 自动部署未成功；
6. Git 流程不合规；
7. 缺少每日群提交或视频未讲清要求。
